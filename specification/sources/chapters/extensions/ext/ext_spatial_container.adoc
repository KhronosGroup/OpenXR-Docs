==== Overview

This extension defines a new class of displayable entities, called "spatial
containers" that are analogous to the concept of "windows" in desktop 2D
windowing systems.

In OpenXR 1.x, apps have exclusive control of all that the user sees and how
that is blended on top of a user's real or virtual environment.
Runtimes only make slight modifications to what is displayed to ensure user
safety.
This app model is good for immersing a user in a single experience, but it
does not extend to multiple simultaneous experiences.
In particular, in AR and mixed reality environments, users often want to
experience multiple different apps at the same time.

Spatial containers are like windows extended to 3D.
The user is able to see multiple spatial containers simultaneously and
provides input to a subset of them.
The visible spatial containers are able to belong to different apps and
runtimes manage their size and placement on behalf of the user.

This extension supports these new types of spatially bounded experiences in
addition to existing immersive OpenXR experiences.
Bounded OpenXR experiences are allowed to have slightly 3D content (flat
panels with minor depth offsets) or volumes that host fully 3D content.
Immersive OpenXR experiences are the existing full-screen immersive apps
that have been supported since OpenXR 1.0.
Apps are able to switch between the two types of content if the app chooses
to.

This extension does not define any method for an app to render its content.
How to draw content is defined in other extensions:
apiext:XR_EXT_spatial_container_self_rendering.

==== Using spatial containers

[open,refpage='XrSpatialContainerEXT',type='handles',desc='Represents a spatial container.']
--
An slink:XrSpatialContainerEXT is a handle that represents a spatial
container.

include::{generated}/api/handles/XrSpatialContainerEXT.adoc[]

An application starts rendering through a spatial container with the
following steps:

1. Create a spatial container with flink:xrCreateSpatialContainerEXT.
2. Modify any state on the container for initial presentation, such as its
   bounds mode.
3. Request the runtime show the container with
   flink:xrRequestSpatialContainerVisibleEXT.
4. Wait for the runtime to be ready to show the container.
   When the runtime is ready, it queues an
   slink:XrEventDataSpatialContainerVisibleChangedEXT event with
   code:visible set to ename:XR_TRUE.
5. Begin rendering for the spatial container.

And tearing down a spatial container is as follows:

1. Request the runtime hide the container with
   flink:xrRequestSpatialContainerVisibleEXT.
2. Wait for the runtime to finish hiding the container.
   When the runtime has fully hidden the container, it queues an
   slink:XrEventDataSpatialContainerVisibleChangedEXT event with
   code:visible set to ename:XR_FALSE.
3. End rendering for the spatial container.
4. Destroy the container with flink:xrDestroySpatialContainerEXT.

[NOTE]
.Note
====
By design, this extension delegates visibility and focus management to
individual spatial containers.
Because the session as a whole no longer represents a single visible or
focused object, the session does not transition through the standard OpenXR
state machine (READY, SYNCHRONIZED, VISIBLE, FOCUSED).
Instead, the session remains in ename:XR_SESSION_STATE_IDLE for its active
lifetime, and the rules in
<<ext_spatial_container-changes_to_session_state>> specify how core OpenXR
operations map to this mode.
====
--

==== Create a spatial container

[open,refpage='xrCreateSpatialContainerEXT',type='protos',desc='Create a spatial container handle.']
--
The flink:xrCreateSpatialContainerEXT function creates a new spatial
container.

include::{generated}/api/protos/xrCreateSpatialContainerEXT.adoc[]

.Parameter Descriptions
****
* pname:session is the slink:XrSession that creates the spatial container.
* pname:createInfo is a pointer to an slink:XrSpatialContainerCreateInfoEXT
  containing parameters to create the spatial container.
* pname:spatialContainer is a pointer to a handle in which the created
  slink:XrSpatialContainerEXT is returned.
****

A newly created slink:XrSpatialContainerEXT must: be not visible, not
interactable, and in bounds mode
ename:XR_SPATIAL_CONTAINER_BOUNDS_MODE_BOUNDED_EXT.
An app that wants a spatial container to start in immersive mode can:
request a bounds mode of
ename:XR_SPATIAL_CONTAINER_BOUNDS_MODE_IMMERSIVE_EXT before requesting to
show a spatial container.

Runtimes must: return ename:XR_ERROR_VALIDATION_FAILURE if any dimension of
slink:XrSpatialContainerCreateInfoEXT::pname:suggestedBounds is negative,
infinite, or not a number.
Runtimes must: return ename:XR_ERROR_LIMIT_REACHED if an app attempts to
create more spatial containers than specified in
slink:XrSystemSpatialContainerPropertiesEXT::pname:maxSpatialContainerCount.
If spatial containers were not
<<ext_spatial_container-changes_to_session_state,enabled for this session>>,
runtimes must: return ename:XR_ERROR_SPATIAL_CONTAINERS_NOT_ENABLED_EXT.

[open,refpage='XrEventDataSpatialContainerClosedEXT',type='structs',desc='Event notifying a spatial container is no longer usable']

When a spatial container is no longer usable, runtimes must: queue an
slink:XrEventDataSpatialContainerClosedEXT event.

include::{generated}/api/structs/XrEventDataSpatialContainerClosedEXT.adoc[]

.Member Description
****
* pname:type is the elink:XrStructureType of this structure.
* pname:next is code:NULL or a pointer to the next structure in a structure
  chain.
  No such structures are defined in core OpenXR or this extension.
* pname:spatialContainer is the slink:XrSpatialContainerEXT that this event

Receiving the slink:XrEventDataSpatialContainerClosedEXT event indicates
that the runtime is no longer able to display a spatial container, for

should: stop using that spatial container, tear down any associated state
such as a render loop, and destroy the container.
Runtimes must: return ename:XR_ERROR_SPATIAL_CONTAINER_CLOSED_EXT from all
functions operating on that container other than
flink:xrDestroySpatialContainerEXT.

runtimes must: first change the container to not visible and queue an
slink:XrEventDataSpatialContainerVisibleChangedEXT event.

The flink:xrDestroySpatialContainerEXT function destroys an existing spatial
container.

include::{generated}/api/protos/xrDestroySpatialContainerEXT.adoc[]

.Parameter Descriptions
****
* pname:spatialContainer is an slink:XrSpatialContainerEXT previously

==== The spatial container space

[open,refpage='xrCreateSpatialContainerSpaceEXT',type='protos',desc='Create a space that is the origin of a spatial container']
--
The flink:xrCreateSpatialContainerSpaceEXT function creates an slink:XrSpace
handle for the spatial container space of a specific spatial container.

include::{generated}/api/protos/xrCreateSpatialContainerSpaceEXT.adoc[]

.Parameter Descriptions
****
* pname:session is the slink:XrSession that creates the space.
* pname:createInfo is a pointer to an
  slink:XrSpatialContainerSpaceCreateInfoEXT containing parameters to create
  the space.
* pname:space is a pointer to a handle in which the created slink:XrSpace is
  returned.
****

The "spatial container space" for any given spatial container is a
coordinate system with its origin at the center of that spatial container's
bounds.
This space is typically used as the base space for functions like
flink:xrLocateSpace.

+X points to the right face of the container, +Y points to the top face of
the container, and +Z points to the front face of the container.
For example, if a container is gravity aligned, in front of the viewer, and
the viewer is at the identity pose relative to the {local_space}, runtimes
must: orient the container space with the identity orientation relative to
the {local_space}.
Runtimes may: set the pose of a container space relative to {local_space} to
any arbitrary pose when that container becomes visible.

image::images/ext_spatial_container_space_convention.svg[opts=inline, align="center", title="Axes convention of spatial container space"]

The spatial container space is a non-world locked origin.
Apps that want a world locked origin while in immersive mode can: use a
world locked space such as ename:XR_REFERENCE_SPACE_TYPE_LOCAL.

Runtimes may: change a spatial container space's pose at any time, commonly
to support a user moving a spatial container to a different position or
rotation.
Runtimes may: also change the pose when transitioning between
ename:XR_SPATIAL_CONTAINER_BOUNDS_MODE_BOUNDED_EXT and
ename:XR_SPATIAL_CONTAINER_BOUNDS_MODE_IMMERSIVE_EXT bounds modes.

A spatial container space must: continue to be a valid handle even if the
spatial container it is for is destroyed with
flink:xrDestroySpatialContainerEXT.
While a spatial container is not visible or destroyed, the spatial container
space must: be <<spaces-action-spaces-lifetime,unlocatable>> relative to
other spaces.
slink:XrSpaceLocation::pname:locationFlags and
slink:XrViewState::viewStateFlags will be 0.

==== Spatial container state

Spatial container state is managed by runtimes based on both app requests
and the needs of the user.
Because of this, each aspect of spatial container state documents the
following things:

* When runtimes are allowed to change the spatial container state.
  For most spatial container state, runtimes may: change the state at any
  time.
* How an app requests changes to the state.
  Runtimes may: defer any request until it believes the request is suitable.
  Runtimes do not queue events when a request is deferred, so apps should:
  not wait on such an event for unrelated logic.
* What event runtimes queue when the spatial container state changes.
  Runtimes queue events for all changes, including app requested changes and
  runtime initiated changes.
  Runtimes must: not queue state change events that do not indicate a
  change, such as if an app makes two requests to hide a container in quick
  succession.
* What event runtimes queue when denying an app change request.
  Runtimes may: deny a request for any reason, typically due to system
  policy related to maintaining a high quality user experience.

==== Visibility

[open,refpage='xrRequestSpatialContainerVisibleEXT',type='protos',desc='Request a change to a spatial container's visibility',xrefs='XrEventDataSpatialContainerVisibleChangedEXT XrEventDataSpatialContainerVisibleRequestDeniedEXT']
--
Apps request to show or hide a spatial container with
flink:xrRequestSpatialContainerVisibleEXT.

include::{generated}/api/protos/xrRequestSpatialContainerVisibleEXT.adoc[]

.Parameter Descriptions
****
* pname:spatialContainer is the slink:XrSpatialContainerEXT to request a
  change for.
* pname:info is a pointer to an
  slink:XrSpatialContainerVisibleRequestInfoEXT containing the requested
  visible state.
****

Showing or hiding a spatial container is an asynchronous operation.

Apps should: request to hide a spatial container before destroying it,
enabling runtimes to display a smooth transition.
Runtimes should: honor requests to hide a spatial container.

A runtime may: deny requests to show a spatial container, in which case the
runtime must: queue an
slink:XrEventDataSpatialContainerVisibleRequestDeniedEXT event.
For example, some runtimes will deny a request to show a spatial container
that the user hid by interacting with a system provided "minimize" button.

Runtimes must: not show a spatial container prior to the app requesting to
show that spatial container at least once.
After the app's first request to show a spatial container, runtimes may:
change the visibility that spatial container independent of an app's
requests.
This enables the app to control the initial state and contents of a spatial
container and enables runtimes to provide system UI like a taskbar that
allow a user to choose which spatial containers are visible.

Runtimes must: deny requests to show a spatial container in a bounds mode
not supported based on
slink:XrSystemSpatialContainerPropertiesEXT::pname:supportsBounded and
slink:XrSystemSpatialContainerPropertiesEXT::pname:supportsImmersive.
This is possible when the default bounds mode,
ename:XR_SPATIAL_CONTAINER_BOUNDS_MODE_BOUNDED_EXT, is unsupported for a
given system.

[NOTE]
.Note
====
On some implementations showing or hiding a spatial container requires
communicating with system services and may: be deferred until after the user
interacts with a system dialog.
The asnchyronous design for requesting visibility state changes is intended
to allow runtimes the time to complete both of these operations.
====

==== Interactable

An app cannot: request a spatial container be interactable.
What spatial containers are interactable is fully controlled by runtimes.
A spatial container that is interactable must: also be visible.

[open,refpage='XrEventDataSpatialContainerInteractableChangedEXT',type='structs',desc='Event reporting interactable state of a spatial container has changed']
--
Every time a runtime changes the interactable state of a spatial container,
the runtime must: queue an
slink:XrEventDataSpatialContainerInteractableChangedEXT event with the new
state.

include::{generated}/api/structs/XrEventDataSpatialContainerInteractableChangedEXT.adoc[]

.Member Description
****
* pname:type is the elink:XrStructureType of this structure.
* pname:next is code:NULL or a pointer to the next structure in a structure
  chain.
  No such structures are defined in core OpenXR or this extension.
* pname:spatialContainer is the slink:XrSpatialContainerEXT that this event
  is for.
* pname:interactable is the new interactable state for the spatial

==== Bounds

A spatial container has a bounds mode and a bounding box.
A spatial container's bounds mode describes how the bounds behave.
Its bounding box is what the spatial container draws inside of.

[open,refpage='XrSpatialContainerBoundsModeEXT',type='enums',desc='Bounding mode of a spatial container']
--
The elink:XrSpatialContainerBoundsModeEXT enumeration identifies different
modes a spatial container's bounds are able to be in.

include::{generated}/api/enums/XrSpatialContainerBoundsModeEXT.adoc[]
include::{generated}/api/enums/XrSpatialContainerBoundsModeEXT.comments.adoc[]

Spatial containers that are in bounds mode
ename:XR_SPATIAL_CONTAINER_BOUNDS_MODE_IMMERSIVE_EXT have additional
requirements:

* Runtimes must: treat these spatial containers the same as a full-screen
  and immersive app created without spatial container usage, except for the
  behavior changes called out in
  <<ext_spatial_container-changes_to_session_state>>.
* Runtimes may: provide additional extensions that enable immersive spatial
  containers to behave differently from full-screen and immersive apps
  created without this extension.
* Runtimes must: report infinite bounds for these spatial containers.
* Runtimes may: hide other spatial containers while an immersive spatial
  container is visible.
  Because this might be different per runtime, apps should: not rely on
  spatial containers being automatically shown or hidden based on immersive
  spatial container visibility.
  Like all other visible state transitions, runtimes must: queue an
  slink:XrEventDataSpatialContainerVisibleChangedEXT event when a spatial
  container is hidden due to an immersive container being visible.

[NOTE]
.Note
====
The above requirements imply that all runtimes can: implement the OpenXR 1.x
path without this extension by implicitly creating a spatial container,
setting the container's bounds mode to immersive, and requesting it be
visible.
====
--

[open,refpage='xrRequestSpatialContainerBoundsModeEXT',type='protos',desc='Request a change to a spatial container's bounds mode',xrefs='XrEventDataSpatialContainerBoundsChangedEXT XrEventDataSpatialContainerBoundsModeRequestDeniedEXT']
--
Apps request to change a spatial container's bounds mode with
flink:xrRequestSpatialContainerBoundsModeEXT.

include::{generated}/api/protos/xrRequestSpatialContainerBoundsModeEXT.adoc[]

.Parameter Descriptions
****
* pname:spatialContainer is the slink:XrSpatialContainerEXT to request a
  change for.
* pname:info is a pointer to an
  slink:XrSpatialContainerBoundsModeRequestInfoEXT containing the requested
  bounds mode.
****

Changing a spatial container's bounds mode is an asynchronous operation and
runtimes may: queue a changed or denied event many seconds after the app
requests a change.
This allows runtimes to pop up UI that is necessary to allow a user to
safely enter an immersive mode.

Runtimes must: honor a request to change the bounds mode for a not visible
spatial container.
If a runtime would deny a bounds mode request for a not visible container,
it instead may: reject or defer a request to show such a spatial container.
This allows apps to start a container as an immersive container.
A runtime may: deny requests to change the bounds mode of a visible spatial
container, in which case the runtime must: queue an
slink:XrEventDataSpatialContainerBoundsModeRequestDeniedEXT event.
For example, some runtimes will deny a request to change the bounds mode of
a visible spatial container that the user is not actively interacting with.

Runtimes must: return ename:XR_ERROR_VALIDATION_FAILURE if an app requests a
bounds mode not supported based on
slink:XrSystemSpatialContainerPropertiesEXT::pname:supportsBounded and
slink:XrSystemSpatialContainerPropertiesEXT::pname:supportsImmersive.

.Member Description
****
* pname:type is the elink:XrStructureType of this structure.
* pname:next is code:NULL or a pointer to the next structure in a structure

While a user is interactively resizing a spatial container, runtimes must:

* queue many events, likely at framerate, as the user is resizing the
  spatial container
* queue a single event at the end of the resize

runtime must: continue to report the old bounds from
flink:xrGetSpatialContainerBoundsEXT until the runtime queues a resize
event.

In other words, if the bounds or bounds mode changes while there is an
slink:XrEventDataSpatialContainerBoundsChangedEXT event still queued,
runtimes must: report only a single event containing the last bounds change
that occurred.
Because apps can: also poll a spatial container's bounds directly with
flink:xrGetSpatialContainerBoundsEXT, the number of bounds changes from
events can: be different the number of changes from polling based on the
timing of runtime generated bounds changes, app calls to flink:xrPollEvent,
and app calls to flink:xrGetSpatialContainerBoundsEXT.

When a spatial container's bounds changes, the spatial container's local
origin may: change as well.
For example, if a runtime allows a user to resize the spatial container's
bounds by dragging one of the container's edges, the bounds and the local
origin for that container will change when the user drags a single edge.
In such situations, the runtime must: change the bounds and the local origin
simultaneously.

height, and depth to 0.0 to represent infinite bounds.
Runtimes must: set pname:infiniteBounds to ename:XR_FALSE and set width,
height, and depth to finite positive numbers for finite bounds.

Runtimes must: set pname:bounds and pname:infiniteBounds following the same
rules as for slink:XrSpatialContainerBoundsEXT.

==== Changes to session state

[open,refpage='XrSessionCreateInfoSpatialContainersEXT',type='structs',desc='Enable spatial containers for a session']
--
Spatial container support is enabled for a session by chaining an
slink:XrSessionCreateInfoSpatialContainersEXT when calling
flink:xrCreateSession.

include::{generated}/api/structs/XrSessionCreateInfoSpatialContainersEXT.adoc[]

When spatial container support is enabled, an slink:XrSession behaves
differently.
This is because when using spatial containers the session no longer presents
image content on the display(s), the spatial containers do so instead.
Therefore, when this extension is enabled a session is effectively
"headless".
Unlike other headless extensions, apps can: submit image data through the
spatial containers.

Enabling spatial container support alters core OpenXR APIs in the following
way.

image::images/ext_spatial_container_session_state_machine.svg[opts=inline, align="center", title="New session state machine"]

* The session never enters the states ename:XR_SESSION_STATE_VISIBLE,
  ename:XR_SESSION_STATE_FOCUSED, or ename:XR_SESSION_STATE_EXITING.
  Runtimes must: never queue events for these states.
  These states are replaced by per-spatial container events
  slink:XrEventDataSpatialContainerVisibleChangedEXT,
  slink:XrEventDataSpatialContainerInteractableChangedEXT, and
  slink:XrEventDataSpatialContainerClosedEXT, respectively.
* The session also never enters the states ename:XR_SESSION_STATE_READY,
  ename:XR_SESSION_STATE_SYNCHRONIZED, ename:XR_SESSION_STATE_STOPPING.
  Runtimes must: never queue events for these states.
  There are no replacement for these states.
* Runtimes must: treat the session as running when it is in the state
  ename:XR_SESSION_STATE_IDLE.
* Runtimes must: treat the session as focused when it is in the state
  ename:XR_SESSION_STATE_IDLE and at least one spatial container exists
  which is interactable.
* The flink:xrBeginSession and flink:xrEndSession functions are no longer
  needed.
  Runtimes must: return ename:XR_ERROR_SPATIAL_CONTAINERS_ENABLED_EXT when
  these functions are called.
  Other extensions may: provide replacements for these functions.
* The flink:xrRequestExitSession function is also no longer needed.
  Runtimes must: return ename:XR_ERROR_SPATIAL_CONTAINERS_ENABLED_EXT when
  this function is called.
  Apps that want to exit a running session instead can: call
  flink:xrRequestSpatialContainerVisibleEXT to hide their containers, and
  destroy the session after all containers are no longer visible.
* Extensions that would queue additional events when the session starts
  running is called now must: queue those events after session creation.
  Such extensions are called out below.

[cols=2*,options='header']
|===
| Extension                          | Event
ifdef::XR_EXT_user_presence[]
| apiext:XR_EXT_user_presence        | slink:XrEventDataUserPresenceChangedEXT
endif::[]
ifndef::XR_EXT_user_presence[]
| `XR_EXT_user_presence`             | `XrEventDataUserPresenceChangedEXT`
endif::[]

ifdef::XR_META_boundary_visibility[]
| apiext:XR_META_boundary_visibility | slink:XrEventDataBoundaryVisibilityChangedMETA
endif::[]
ifndef::XR_META_boundary_visibility[]
| `XR_META_boundary_visibility`      | `XrEventDataBoundaryVisibilityChangedMETA`
endif::[]

|===

* The flink:xrLocateViews function is not valid to call for the session.
  Runtimes must: return ename:XR_ERROR_SPATIAL_CONTAINERS_ENABLED_EXT from
  flink:xrLocateViews.
  Other extensions may: provide ways to locate the views for a particular
  spatial container.
* The flink:xrWaitFrame function must: always set
  slink:XrFrameState::pname:shouldRender to false.
  Other extensions may: provide ways to know if a particular spatial
  container should: update its composition layers.
* The flink:xrEndFrame function is not a valid way to submit composition
  layers.
  If an app sets slink:XrFrameEndInfo::pname:layerCount to a non-zero value,
  runtimes must: return ename:XR_ERROR_VALIDATION_FAILURE.
  Other extensions may: provide ways to submit composition layers for a
  particular spatial container.
* Entering the state ename:XR_SESSION_STATE_LOSS_PENDING also closes all
  spatial containers.
  Runtimes must: queue an slink:XrEventDataSpatialContainerClosedEXT event
  for each active spatial container before queueing a session state change
  for ename:XR_SESSION_STATE_LOSS_PENDING.
* The flink:xrCreateSession function no longer needs a graphics API binding
  structure.
  Other extensions may: require a graphics binding, for example for a
  spatial container to render using a graphics API.

The above behavior is slightly different from the behavior in
apiext:XR_MND_headless.
Runtimes must: not enable the headless session behavior from
apiext:XR_MND_headless when spatial container support is enabled for that
session.

[NOTE]
.Note
====
When spatial containers are enabled, a session transitions between only two
states: ename:XR_SESSION_STATE_IDLE (running) and
ename:XR_SESSION_STATE_LOSS_PENDING (not running).
As a result, runtimes no longer return ename:XR_ERROR_SESSION_RUNNING or
ename:XR_ERROR_SESSION_NOT_RUNNING.
Instead, when a session is not running, runtimes return either
ename:XR_ERROR_SESSION_LOST or ename:XR_SESSION_LOSS_PENDING following the
rules in OpenXR core.
Furthermore, flink:xrBeginSession, the only function that returns
ename:XR_ERROR_SESSION_RUNNING, will now always return
ename:XR_ERROR_SPATIAL_CONTAINERS_ENABLED_EXT.
====

==== Android Manifest entries

AOSP based runtimes may: have custom behavior based on the initial spatial
container state that is started before running any app code.
For example, a runtime may: alter resources allocated for the activity,
launch animations, or splash screen display.
The following properties are provided for this purpose.
They replace the `<category
android:name="org.khronos.openxr.intent.category.IMMERSIVE_HMD" />` tag,
which spatial container based apps should: not specify except for
compatibility with earlier AOSP based runtimes.

[source,xml]
----
<property android:name="org.khronos.openxr.PROPERTY_ACTIVITY_HINT_XR_SPATIAL_CONTAINER_USED_BOUNDS_MODES"
          android:value="list of modes" />
----

This property hints to runtimes that the bounds modes used by an activity.
By default it is an empty list, which implies no hint.

The following strings are valid for this attribute.
Multiple values are separated by `|`, such as `"bounded|immersive"`.

[cols=2*,optionsn='header']
|===
| Value         | Description
| `"2d_panel"`  | The activity displays using Android's 2D view framework.
| `"bounded"`   | The activity uses ename:XR_SPATIAL_CONTAINER_BOUNDS_MODE_BOUNDED_EXT.
| `"immersive"` | The activity uses ename:XR_SPATIAL_CONTAINER_BOUNDS_MODE_IMMERSIVE_EXT.
|===

[source,xml]
----
<property android:name="org.khronos.openxr.PROPERTY_ACTIVITY_HINT_XR_SPATIAL_CONTAINER_INITIAL_BOUNDS_MODE"
          android:value="XR_SPATIAL_CONTAINER_INITIAL_BOUNDS_MODE_BOUNDED|
                         XR_SPATIAL_CONTAINER_INITIAL_BOUNDS_MODE_IMMERSIVE|
                         XR_SPATIAL_CONTAINER_INITIAL_BOUNDS_MODE_UNDEFINED" />

This property hints to runtimes the activity's initial
elink:XrSpatialContainerBoundsModeEXT when it is first created.
By default it is the string
XR_SPATIAL_CONTAINER_INITIAL_BOUNDS_MODE_UNDEFINED, which implies no hint.

Runtimes must: not require apps to have these properties to otherwise behave
according to this spec.
Runtimes must: not alter app visible behavior based on these properties.
All such metadata must: be specifiable at either the <activity> level or the
<application> level.
If specified at the <application> level, it applies to all activities in the
application that do not specify their own values.

==== Example code

The following code shows how to use this extension for perception-only use
cases without any rendering.

[source,cpp]
----
XrInstance instance;    // Already initialized


// Create the session with spatial containers enabled
XrSession session;

XrSessionCreateInfoSpatialContainersEXT spatialContainerCreateInfo {
  .type = XR_TYPE_SESSION_CREATE_INFO_SPATIAL_CONTAINERS_EXT,
};
XrSessionCreateInfo sessionCreateInfo {
  .type = XR_TYPE_SESSION_CREATE_INFO,
  .next = &spatialContainerCreateInfo,   // Enable spatial containers
};
(void)sessionCreateInfo.systemId;                             // Other create fields set in usual way

CHK_XR(xrCreateSession(instance, &sessionCreateInfo, &session));


// Because spatial containers are enabled, the session is considered
// running. App is able to query perception data such as head poses and hand
// poses.


// Based on app logic or when a system lost event happens, destroy the
// session
CHK_XR(xrDestroySession(session));
----

==== Issues

* How do we handle multiple outstanding visible requests? Should the app get
  one change / denied back or multiple? The answer might be different if the
  calls are over multiple frames.
  The answer might also be different if the multiple requests result in a
  noop, i.e. requesting a spatial container to be visible, then not visible
  for a container that starts out not visible.
** **Resolved.
   Different choices for change events and denied events.** Noop requests do
   not queue a change event, this just generates noise for the app developer
   and is easy for runtimes to filter out.
   If multiple visible requests get denied, runtimes must: each generate a
   corresponding denied event.

* How is a conformance automation extension expected to be defined so that
  all the optional spec text for policy behaviors is still testable by CTS?
** **Resolved.
   Separate test extension.** There will be a test extension runtimes
   implement for CTS only, allowing CTS to control all the system policy.

* Do we need an event for when a spatial container's position changes?
** **Resolved.
   No.** The spatial container space is non-world locked and other such
   spaces, like ename:XR_REFERENCE_SPACE_TYPE_VIEW, do not have events when
   they change.

* How does flink:xrSyncActions work if there are multiple spatial
  containers?
** **Resolved.
   No change needed.** flink:xrSyncActions would apply to all spatial
   containers in the session.
   If an app wants to direct the input actions to a particular spatial
   container it can: look at interactable per-container state to choose
   which containers are valid targets.
   If an app wants to only sync the input action state for a single spatial
   container that would require an additional extension.
   However, we expect to instead focus on an extension that allows apps to
   be fully event based and avoid the need for an flink:xrSyncActions call
   in a frame loop.

* How does infrequently updated apps deal with input?
** **Resolved.
   No change needed.** While valuable to EXT_spatial_container, it is also
   valuable outside of spatial containers.
   This is able to be handled via an event channel extension and work in
   both cases.
   For spatial containers we will add additional ways to filter events for a
   single spatial container.

* Do we need a wait to throttle / control timing of the input loop for apps
  with decoupled input and rendering loops?
** **Resolved.
   No change needed.** This is expected to be handled via event channel and
   present request extensions.
   Present request extension allows rendering to be event based and
   decoupled from a frame loop.

* Can a spatial container get its pose relative to other spatial containers?
  Key thoughts here: Do we have a use case for this? And if so, how do the
  spatial container spaces connect to LOCAL?
** **Resolved.
   Yes.** This is already possible for spatial containers within the same
   session by going through ename:XR_REFERENCE_SPACE_TYPE_VIEW and
   supporting view-dependent content is desirable.
   For sharing spatial container poses across sessions (like to another
   process) the expected path is to leverage apiext:XR_EXT_spatial_anchor
   and its existing persistence and sharing patterns.

* Is a spatial container's space locatable if it is not visible?
** **Resolved.
   No.** The spatial container's space is not locatable when the spatial
   container is not visible.
   This implies that it does not have spatialized audio nor is the app able
   to "warm up" view dependent content when the spatial_container is not
   visible.
   These are both ok because when a spatial container is not visible, the
   app is expected to stop any CPU / GPU load that is used for that spatial
   container.

* Where is the spatial container space expected to be placed in the spatial
  container? Suggestions have been the center or the minimal point (minX,
  minY, minZ).
** **Resolved.
   In the center.** There is no location that does not move in most of the
   ways a spatial container resize UX is expected (moving edges).
   Center is commonly used in other parts of OpenXR.
   We did not align with windows in 2D computing, which use the minimum
   coordinate, because 3D model viewers often do not follow this convention.

* When is a runtime expected to create resources underlying the spatial
  container? This sometimes involves IPC with system services.
** **Resolved.
   Synchronously as part of ftext:xrCreateSpatialContainerEXT.** While there
   might be IPC involved, the actual creation of a container is generally
   expected to be cheap.
   Some vendors have global mutexes around managing containers but these are
   not expected to commonly be a long wait.
   Issues with mutex contention are vendor-specific bugs that are expected
   to get addressed by each vendor.

* Do we need a signal that an slink:XrSession will create spatial containers
  and therefore not support the legacy rendering path?
** **Resolved.
   Yes.** We change the session state machine in a fundamental way.
